## 1 Introduction

This project is a small web application for storing and managing personal files. Users can register, sign in, upload PDF or text documents, view their own files, download them and delete them. File contents are encrypted on the server before they are written to storage.

The aim is to apply the security topics covered in the course: authentication, session management, authorization, encryption, input validation, injection prevention and protection against forged requests. A working page is not sufficient; the server must reject a request that breaks its rules even when someone changes the information sent by the browser.

The application is intended for a local HTTPS demonstration on Windows. File sharing, public hosting and document previews are outside the scope. The server holds the encryption keys, so this is server-side encryption, not end-to-end encryption.

## 2 Implementation

### Architecture and technology choices

The browser displays HTML generated by Flask and Jinja and sends requests over HTTPS. Flask applies the application rules. SQLAlchemy connects Flask to SQLite, which stores users, password hashes, sessions, file metadata and deletion markers. Separate private folders hold encrypted file contents and their encryption keys.

The main trust boundary is between the browser and the application: browser input is untrusted. The server obtains the current user from its session and checks database ownership before accessing storage. The database, storage and key folders are outside public web routes. Their separation does not protect against complete compromise of the server.

Flask keeps the project manageable, while SQLite avoids a separate database service. The cryptography library supplies AES-GCM, and argon2-cffi supplies password hashing. Flask-WTF, Flask-Session and Flask-Limiter provide CSRF protection, server sessions and request limits. Exact dependency versions are recorded in requirements.txt.

### Authentication and sessions

Registration validates credentials on the server. Passwords contain 15–128 characters and are stored as salted Argon2id hashes, rather than readable passwords. Login uses generic failure messages and performs a dummy hash check for unknown users to reduce timing differences.

The browser receives a random session identifier; session data stays in SQLite. The cookie uses Secure, HttpOnly and SameSite=Lax. Login rotates the identifier to prevent fixation, logout invalidates it, and the server enforces a 15-minute idle timeout and a two-hour absolute lifetime. Rate limits restrict repeated login and file operations.

### File validation and encryption

The upload endpoint accepts one nonempty PDF or UTF-8 TXT file of at most 5 MiB. It rejects unsupported extensions, path separators, binary text and files that fail basic format checks. It does not trust the browser-provided MIME type. Display names are normalized, while random internal identifiers are used for storage paths.

Before encryption, upload data stays in bounded application memory. Each file receives a fresh random 256-bit key and a 12-byte nonce. AES-256-GCM encrypts the contents and provides an authentication tag. The file identifier, owner, filename, type and size are authenticated as additional data, so changing those values also causes verification to fail. The key is saved separately from the encrypted file on the same host. [2]

### Download, deletion and TLS

Listing, download, deletion confirmation and deletion are restricted to the authenticated owner. Download queries include both the file identifier and the session user. Unknown files and another user’s files receive the same 404 response. The full ciphertext is authenticated before any plaintext is returned.

Downloads use attachment, octet-stream and nosniff headers; file contents are not embedded into a web page. Deletion requires a confirmation page followed by a CSRF-protected POST. A durable deletion marker is saved before removing the key, ciphertext and database record. An interrupted deletion stays unavailable for download and can be retried. This does not guarantee physical erasure from an SSD or from backups.

Local HTTPS uses a certificate generated with mkcert. The development server accepts TLS 1.2 or newer, listens only on 127.0.0.1:5000 and runs with debugging disabled. The application secret, certificates, file keys and runtime data are excluded from Git.

### Error handling and security logging

Invalid requests receive appropriate HTTP errors. Unexpected failures return a generic 500 page, roll back the current database transaction and do not expose stack traces, SQL parameters or filesystem paths.

Checkpoint 3 adds private JSON logs in instance/logs/security.jsonl. Request events record the UTC timestamp, event, severity, source address, HTTP method, endpoint and a server-generated request ID. The account identifier is included when known; outcome/status and internal file identifiers are recorded where relevant. Anonymous events do not record the session cookie. X-Request-ID in the response allows correlation with the private log.

The source address is taken from the connection, validated as an IP address and recorded as null if unavailable or invalid. Because this setup has no trusted proxy, client-supplied Forwarded and X-Forwarded-For headers cannot replace it. This field was added after checking the logging requirement on page 10 of the project brief. [1]

Logs cover authentication, rejected CSRF, denied access, file operations and errors. They exclude passwords, tokens, cookies, filenames, file contents and raw exception messages. Files rotate at approximately 1 MiB, with three backups. A runtime log-write failure emits a fixed warning without reversing a successful operation. Logging uses the Python standard library and adds no dependency. [3]

## 3 Security Analysis

The following local test cases demonstrate the main threats and their mitigations. Each result describes an attempted case, rather than a guarantee that every possible attack is prevented.

- **CSRF:** Registration, login, logout, upload and deletion were submitted with missing, forged and foreign-session tokens. All 15 requests returned 400 and existing data remained unchanged. A deletion with a valid token but a foreign HTTPS Referer was also rejected. Global Flask-WTF token validation and the HTTPS origin check protect these operations; SameSite is an additional defence. [4]

- **Reflected and stored XSS:** A login username containing "&gt;&lt;img src=x onerror=alert(1)&gt; and filename metadata containing an img/onerror payload were tested. HTML parsing found no injected elements; the text was escaped. Jinja output escaping is the primary control, supported by a CSP with script-src 'none'. A TXT containing &lt;script&gt;alert("test")&lt;/script&gt; was returned only as a download attachment.

- **SQL injection:** Login inputs included ' OR '1'='1, admin'-- and '; DROP TABLE users;--. All returned 401, and the users table remained intact. A separate test captured the real login query and verified that the username was passed as a bound parameter, separately from the SQL text. Application queries use SQLAlchemy parameter binding. [5]

- **Broken access control:** A second account used the owner’s file ID to request download, deletion confirmation and deletion, including a valid token for the second account. Each request returned 404, while the owner retained access. Listing is also owner-scoped, and a submitted owner_id cannot change upload ownership.

- **Upload tampering:** Attempts included ../outside.txt, Windows paths, unsupported extensions, empty or binary TXT data and a fake PDF labelled application/pdf. They returned 400. A 5 MiB file was accepted; one byte over the limit returned 413. Server validation and generated storage identifiers prevent bypassing browser controls.

- **Encrypted-data tampering:** Modified ciphertext, nonce, header, key, metadata and file length caused a 503 response without a plaintext attachment. Restoring the original data restored download. AES-GCM authentication and format checks detect these changes before sending the file.

- **Error disclosure and log injection:** A simulated exception containing private text produced a generic 500 response. CRLF/forged JSON input and a forged request-ID header did not inject log records or expose secrets. Logs remained valid JSON and recorded only selected fields. A simulated logging failure did not break login.

- **Source-address spoofing:** A new test supplies fake forwarding headers with IPv4, IPv6, missing and invalid connection addresses. The log records the validated connection address or null, never the supplied forwarding-header value.

The suite also covers expiry, logout and session-ID replay, request limits, exact download contents, storage failures and interrupted deletion. Source review found no interpolated raw application SQL, unsafe template rendering or CSRF exemptions.

[Full case matrix, test names and reproduction steps](https://github.com/jpaulobaptista2000-code/secure-file-manager/blob/checkpoint-3/docs/checkpoint-3-security-tests.md)

### Testing and observed results

The latest automated run, on 14 November 2026, completed 75 tests in 16.536 seconds on Linux with Python 3.12.14: all passed, with no failures, errors or skips. This covers the 58 Checkpoint 2 tests and 17 Checkpoint 3 cases, including the new source-address test. The tested source is recorded in commit 079a765.

The Windows run supplied on 14 November completed 74 tests in 17.378 seconds: OK (skipped=2), meaning 72 passed. This run preceded the source-address addition. The two skips concern POSIX permission bits; they do not verify Windows ACLs. The additional source-address test has passed on Linux but has not yet been confirmed on Windows.

Automated tests use Flask’s test client with an HTTPS base URL and disposable databases, files and logs. They test request handling without a browser or a real network TLS handshake. The complete Linux output and the supplied Windows summary are retained as separate evidence files.

In the Windows HTTPS browser demonstration, replacing the deletion token with forged produced the security-token error page. The file remained listed and downloaded with its original contents. Opening the owner’s download link from a second account in a private browser window returned File not found. Inspection of the private log confirmed csrf_rejected / 400 and file_access_denied / 404. The report summarizes these observations without publishing the original runtime identifiers.

### Remaining limitations

A server compromise could expose both keys and files; database metadata is readable. PDF validation checks basic markers, not malware, and opening downloads in an external viewer carries its own risk. Memory buffering does not control operating-system swap or crash dumps. There is no account-wide storage quota or automatic reconciliation of orphan uploads after an abrupt crash.

Rate-limit counters reset on restart. Logs are local, have bounded retention and are not tamper-resistant against a server administrator. Existing Windows directory ACLs are not repaired automatically. Production deployment, external key management, remote logging and dependency vulnerability scanning remain future work. Passing these tests does not establish that the application has no vulnerabilities.

## 4 Conclusion

The planned local account and file-management flows are implemented. Checkpoint 3 adds structured security logging, safer error handling and explicit attack evidence. The submitted Checkpoint 2 remains on main; Checkpoint 3 is developed separately with incremental commits. The draft now covers the four report sections requested in Section 1.3 and the checkpoint evidence requested in Section 3.4.3. [1]

The main learning point is that different controls solve different problems: authentication identifies a user, ownership checks decide which files they may access, hashing protects stored passwords, file encryption protects stored contents, and TLS protects transport. CSRF protection does not replace authorization, so both must be tested independently.

Practical challenges included setting up Python and Git on Windows, making mkcert available in PowerShell and trusting the local certificate. Security testing also required checking what happens after rejection or failure, such as confirming that a forged deletion did not remove the file. Reviewing the full brief identified the missing source-address field, which was added and tested. Before final submission, the new Windows check and final report review remain to be completed.

## Appendix A: Running the application on Windows

Prerequisites: Python 3.13 or newer, Git for Windows and mkcert. If mkcert is missing, install it with the command below and reopen PowerShell. Run each line from PowerShell; a backtick continues the same command on the next line.

```powershell
winget install --id FiloSottile.mkcert --exact --source winget
```

### 1. Clone the checkpoint and install dependencies

```powershell
Set-Location $env:USERPROFILE
New-Item -ItemType Directory -Force Projects | Out-Null
Set-Location Projects
git clone --branch checkpoint-3 `
  https://github.com/jpaulobaptista2000-code/secure-file-manager.git `
  secure-file-manager-checkpoint3
Set-Location secure-file-manager-checkpoint3
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 2. Create the local HTTPS certificate

```powershell
mkcert -install
New-Item -ItemType Directory -Force certs | Out-Null
mkcert -cert-file certs/localhost.pem `
  -key-file certs/localhost-key.pem localhost 127.0.0.1 ::1
```

Approve the Windows certificate prompt. Generate certificates on each computer; keep private keys out of Git. The TLS key is separate from the keys used to encrypt uploaded files.

### 3. Start and use the application

```powershell
.\.venv\Scripts\python.exe run.py
```

Keep PowerShell open and visit https://127.0.0.1:5000 in Edge or Chrome. First startup creates the database and private folders. Register, sign in, upload a small TXT or PDF, download it and try deletion. Keep the instance folder between restarts. Stop the server with Ctrl+C.

### 4. Run the automated tests

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The current suite contains 75 tests. Windows skips two POSIX permission checks. Tests use disposable data and leave normal accounts and uploads untouched.
